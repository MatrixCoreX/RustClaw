# 分布式媒体下载节点防作恶学习笔记

日期：2026-10-24

状态：方案讨论，尚未据此新增防作恶机制。

## 核心结论

可以大幅降低恶意节点带来的风险，但不能保证陌生节点绝不作恶。节点用户控制自己的电脑，可以修改下载程序，也可以伪造执行结果。

最关键的问题是：节点上传了一个能播放的视频，服务器怎么确认它就是用户链接对应的视频？

签名只能证明哪个节点提交了结果。服务器校验 SHA256，只能证明收到的文件与声明的摘要一致。恶意节点完全可以上传另一个视频，同时提交那个视频的正确摘要。因此，身份认证和文件完整性校验都不能单独证明媒体内容真实。

## 风险与防范办法

| 可能的作恶方式 | 防范办法 | 能力边界 |
| --- | --- | --- |
| 领取任务后一直拖着 | 限制同时领取数量，设置任务总时限；即使持续心跳也不能无限续期，超时后换节点 | 可以限制单个节点造成的影响 |
| 上传损坏文件、危险文件或压缩炸弹 | 服务端限制体积、实际格式、压缩展开量；隔离检查文件，并限制检查过程消耗的资源 | 能拦截很多异常，不能只相信扩展名和 MIME |
| 偷换视频、图片或文章 | 由可信节点随机复核，异常结果交给可信节点重新采集 | 节点自己提供的元数据无法单独证明内容真实性 |
| 污染公共缓存 | 未验证结果先隔离；发现问题后撤销缓存并重新下载 | 缓存应记录来源节点，支持追查和批量撤销 |
| 注册大量节点控制结果 | 审核准入，限制新节点任务量，逐步建立信誉 | 多节点投票也可能被同一个人控制，节点数量不等于独立参与者数量 |
| 窃取用户信息 | 只下发必要的媒体链接和输出要求，不下发用户身份、网站登录 Cookie 或服务器密钥 | 执行下载的普通节点仍能看到链接和媒体内容 |

文件检查需要多层组合，单个格式或文件头检查不足以保证安全。参考 [OWASP 文件上传安全指南](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)。

## 两个容易误判的地方

- 两个节点下载结果的哈希不同，不一定有人作弊。不同清晰度、封装或转码会产生不同文件，不能仅凭哈希不同就封禁节点。
- 下载失败不一定是作恶。平台限流、登录失效、网络故障应与伪造结果分开处理。

## 适合当前项目的推进方式

先让自己和经过审核的家庭节点接生产任务。将来开放陌生节点时，先限制任务量，再通过可信节点抽查，合格后逐步放量。

不要仅凭安装了官方程序、能签名、心跳正常，就认定节点可信。普通节点的所有者可以修改程序，也可以绕过官方程序直接构造协议请求。

身份、限额和超时机制主要控制谁能参与、能造成多大影响；文件检查主要识别异常文件；可信节点复核用于增加对媒体来源和内容正确性的信心。这几类措施需要配合使用。

## 更强保证的研究方向

如果要进一步限制节点主人篡改执行过程，需要研究硬件可信执行和远程证明，部署成本与硬件要求都会增加。仍然需要明确证明覆盖哪些程序、输入和执行环节，不能直接把运行环境证明等同于媒体内容正确性证明。参考 [IETF RFC 9334 远程证明架构](https://www.rfc-editor.org/rfc/rfc9334.html)。

## 后续学习与设计问题

- 如何建立和管理经过审核的节点名单，并处理密钥撤销与节点退出？
- 如何设置任务总时限，防止节点持续续租却始终不交付？
- 如何隔离检查视频、图片、音频和 ZIP，同时限制 CPU、内存与磁盘消耗？
- 如何选择可信复核节点，并处理同一媒体不同清晰度或封装造成的差异？
- 如何记录产物与缓存的节点来源，在发现问题时撤销相关结果？
- 如何区分平台故障、普通节点故障和有证据的恶意行为，避免误罚？

上述问题保留用于后续学习与设计，不代表当前功能已经实现。
